# Durable native recovery accounting: source integration and enrollment

This is a controlled, bounded fault-scope integration, not production/P2 qualification. `NativeRecoveryAccountingConfiguration` is actor-profile-only and requires an explicit trusted `NativeRecoveryEnrollment` bean. There is no public enrollment endpoint, automatic cohort inferred from a scan, default privacy key, or guessed fault timestamp.

The provider must supply a complete pre-fault roster, source digest, privacy key/key ID, cohort UUID and PROCESS/AZ fault kind. Call `capture(Cohort)` and await its original physical completion before causing the fault; call `fault(UUID, actualFaultAt)` with the actual fault timestamp. Both capture freshness and fault-report freshness are five seconds. Reusing a UUID requires the exact original manifest; retries cannot reset deadlines or add denominator members. PROCESS reattachment is 60 seconds; AZ reattachment is 180 seconds; convergence is 30 seconds; preservation uses a separate 60-second observation window (not a qualified preservation target) and media continuity is 30 seconds.

A cohort contains at most 128 calls and 640 SLI memberships. One authority-guarded SQL transaction seals the entire declared scope. Native cell/storage epoch, group/grant/current bucket and snapshot eligibility are checked. Active eligibility must match the native state; media eligibility additionally requires both media flags and trusted provider confirmation of healthy pre-fault media. The provider is responsible for completeness and actual pre-fault media health. This API cannot qualify a larger/unplanned fault by sampling or splitting its denominator. Larger complete paginated fault sources remain missing inputs.

V017 stores HMAC membership/manifest digests and fixed counters, never raw call/user/session IDs, routes, SDP, ICE, tokens or command payloads. Admission is globally bounded to 64 cohorts and 8192 memberships; capacity includes unresolved and completed cohorts, with no eviction/reset API. Saturation fails admission. Operators must define audited retention/key rotation before sustained production use. Epoch/key changes retain denominator evidence and make accounting UNKNOWN.

Native success sources are separate:

- Convergence: owner-confirmed guarded hydration under the same original authority token, or an authorized committed terminal snapshot with a terminal reason. A live snapshot read is insufficient.
- Active preservation: current native authorization with both signed ACTIVE home proofs and the retained activation/winner.
- Signaling reattachment: validated application receipt after exact current full-route authorization; socket admission/write is insufficient.
- Media continuity: actual post-fault authenticated peer media observations for both peers in the same current round, followed by current both-ACTIVE-home proof. Persisted media flags alone are insufficient.

SQL revalidates hooks under current authority, fixed fault/deadline/version/round conditions and atomic `successful_at IS NULL` dedup; cumulative totals update in the same transaction. Duplicates and restart do not increment eligible/success twice. Missing fault cohorts, expired unresolved observations, dropped/overloaded callbacks, stale metric reads and incompatible epoch/privacy binding keep ratio UNKNOWN/NaN. They are not fabricated successes or measured failures. Outcomes queued during shutdown can be lost; persisted unresolved members remain visible and expire UNKNOWN. This bounded producer has no durable observation retry queue.

The producer retains at most64 trusted volatile cohort manifests (<=128calls each),32 pending typed observations and16 original SQL physical owners. The trusted provider must replay exact manifests through capture after restart and replay fault with the same original timestamp; the HMAC journal cannot reconstruct raw membership. Only captured, armed, exact call/SLI/participant memberships within their original window enter the queue. Membership publishes after proven capture COMMIT and physical completion; arming precedes fault SQL so concurrent observations are retained, but outcome SQL waits for fault resolution. Ready cohorts bypass unresolved fault admissions. Loss is bounded to the affected cohort IDs; only resolved fault admissions are acknowledged from the loss journal, preventing pre-COMMIT loss from being erased. Already fully successful cohorts are not invalidated by redundant later losses. Runtime manifests are volatile and raw identities are never added to the DB journal. Hooks enqueue without changing business authority outcomes. SQL uses existing RECOVERY maximum admission charges and two-second logical budgets; physical completion remains owned through drain. Durable metrics are gauges backed by shared SQL cumulative totals, with fixed `sli` labels and existing cell enrollment. Aggregate duplicate pod eligible/success gauges with `max by(cell,sli)`, never `sum`; compute ratio from known fresh values, preserving UNKNOWN. Per-pod freshness is five seconds. These metrics do not replace fault-specific external qualification evidence.

Required external inputs: trusted complete fault provider and actual timestamp contract, privacy key/Secret reference, large-fault source, retention/rotation policy, real client telemetry and application receipt integration, rollout/deployment environment and P2 evidence. DB migration execution, concurrency/restart/fault behavior and browser/mobile runtime are unrun. Do not erase V017 evidence on rollback; disable enrollment/receipt capability and retain accounting rows. Old binaries must not be treated as outcome producers.
