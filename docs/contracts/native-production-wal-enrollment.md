# Native WAL observation and production input boundary

The repository pins PostgreSQL 17.6 and CloudNativePG 1.27.0 in `deploy/postgres/cloudnativepg-cluster.yaml`. `PostgresWalFacts` reads through the existing admitted `SqlTransactions` owner, on `DbClass.RECOVERY`, with a maximum two-second logical budget and original physical completion. It samples cell/epoch/ACTIVE/GROUPED/schema identity, writer role, `pg_control_system().system_identifier`, and the timeline encoded by `pg_walfile_name(pg_current_wal_flush_lsn())`. A second identity sample fences changes across replication observation. No checkpoint timeline is accepted as current-writer proof.

A deployment supplies `NativeWalEnrollment` with exact current writer system identifier/timeline, expected replica `application_name` values (maximum eight), required synchronous count, maximum byte lag and explicit source/reply freshness. The existing SQL connection/TLS enrollment supplies the admitted writer endpoint. Replicas are observations of authenticated replication connections in that writer's `pg_stat_replication`, not independently authenticated standby SQL endpoints. The enrollment depends on operator-controlled replication identities; an arbitrary application's self-selected name is not enrollment. Missing replicas, extra/duplicate identities, stale replies, role/epoch mismatch, denied SQL privileges, NULL positions, unsupported major version, or partial statistics deny readiness. Direct standby SQL replay timeline identity and promotion/acknowledged-WAL evidence remain unsupported and unknown.

`NativeWalConfiguration` creates the owner only with explicit enrollment and matching actor cell/epoch. It attaches once to `NativeActorSafetySources`; `jobs()` schedules the SAFETY probe, and source drain waits for its original physical owner. Missing enrollment denies WAL readiness even when primary-valid succeeds. Explicit `localSingleWriter` requires the `local-test-only` profile and empty replica requirements; this makes no HA claim. No automatic local fallback is supplied.

Metrics are fixed and contain no endpoint/replica labels: `signaling.wal.source.age.seconds`, `signaling.wal.flush.lag.bytes`, and `signaling.wal.replication.flush.seconds`. Age and byte lag are not durations of replication. NULL replication durations remain NaN, including idle replica observations; they never become zero. PostgreSQL 17.6 duration reporting has version-specific limitations, so duration is informational and is not an admission predicate. High observed byte lag remains measurable when the WAL policy rejects admission.

## Production loader

`MountedProductionContract.load(file, approvedMountRoot, activeProfiles)` is a separate explicit API. It does not call `MountedNativeContract`, load local enrollment, create a provider client, register beans, or start a deployment. Schema version 1 requires exactly one plane (`actor`, `gateway`, or `control`), `environment=production`, complete cell/epoch and non-local WAL policy, database provider contract, and mounted path/SHA-256 references for operator attestation, identity contract, workload trust, cell/directory DB enrollment, clock/revocation sources, physical-fence implementation, witness implementation, and acknowledged-WAL manifest. Unknown/missing fields, duplicate JSON properties, scalar coercion, trailing content, profile mismatch, unresolved substitutions, unbounded files, references outside the approved mount root, and digest mismatch reject loading.

The approved mount and reference digests are an operator trust boundary. A matching digest establishes file integrity under that trust boundary, not an independently verified provider receipt. Provider-specific content validation, signature/expiry verification, exact issuer APIs, physical fence execution, witness topology verification, and acknowledged-WAL restoration validation must be implemented against actual supplied contracts. The loader deliberately does not interpret opaque provider files or invent their protocol. Recovery-journal enrollment can be added as a future explicit schema extension; arbitrary extra fields currently reject.

## Render-only provider patch

`NativeDatabaseProviderRenderer.render(contract, objectName, endpointCa)` returns a CNPG Cluster patch plus Barman ObjectStore. S3 uses only accessKeyId/secretAccessKey/optional sessionToken references; Azure uses connectionString; GCS uses applicationCredentials. Explicit Secret name/key references are emitted, never values. The CA key must be supplied and its Secret name must match the typed contract. Durations that would lose precision reject rendering. Plugin version/image digest are preserved as an operator installation requirement comment; rendering does not install or verify the plugin image, encryption key, network policy, or fencing provider. The existing `provider-overlay.yaml.tpl` remains an S3-only input template; it is not a production manifest or a fallback renderer.

Required external inputs remain actual identity issuer/trust; approved mounted attestation and endpoint credentials; the deployed writer system identifier/timeline and replication identities; the fence/witness APIs and signed evidence schema/keys; acknowledged-WAL manifest format/source; plugin installation pin and provider tuning qualification evidence; archive credentials, CA, encryption/network policy and isolated restore target. Neither loaded input nor generated YAML is deployment, recovery, or promotion success.

Sources: [PostgreSQL 17 administration functions](https://www.postgresql.org/docs/17/functions-admin.html), [PostgreSQL 17 replication statistics](https://www.postgresql.org/docs/17/monitoring-stats.html), [Barman provider credential fields](https://cloudnative-pg.io/plugin-barman-cloud/docs/0.14.0/object_stores/). The runtime query must still be exercised against the pinned image and real grants; no tests, database probes, deployment or qualification were run for this change.

### Synchronous acknowledgement policy

Both identity samples read the actual `synchronous_standby_names`; changes across sampling reject the observation. The accepted bounded grammar is explicit `FIRST n (names)` or `ANY n (names)` with 1–8 required acknowledgements and no more than eight concrete names (simple identifiers or quoted ASCII application names). Wildcards, duplicates/case aliases, implicit legacy syntax and unsupported quoting reject conservatively. Actual required count must equal the enrolled count, and all configured identities must equal the enrolled set. ANY `quorum` rows count as available candidates only after this policy binding; they never establish the acknowledgement threshold by themselves. FIRST additionally requires exactly the configured count of `sync` rows. An empty setting is valid only for the explicit local single-writer policy. Thus `ANY 1 (a,b)` cannot satisfy a two-acknowledger enrollment. [PostgreSQL policy semantics](https://www.postgresql.org/docs/17/runtime-config-replication.html#GUC-SYNCHRONOUS-STANDBY-NAMES).
