# PITR and acknowledged-history loss

Run only in an approved isolated recovery target. A real backup, WAL archive, native topology, enrolled fencing/identity sources and approved restoration point are prerequisites. `pitr-restore.sh --dry-run` tests PostgreSQL epoch repair against real local PostgreSQL; it does **not** restore a production backup or certify RPO/RTO.

1. Stop new admission and freeze the affected cell/directory namespace. Export approved external recovery authorization and the latest **pre-disaster storage-epoch high-water** from an authority outside the restored backup. Prove physical fencing of every old writer and workload that could still mutate this target. Preserve fault and acknowledged-operation/WAL timelines.
2. Restore through the pinned CloudNativePG controller into a new isolated cluster using the approved backup/WAL target. Supply the actual backup provider/plugin configuration and exact image digests; backup egress is explicitly reviewed. Verify backup integrity, actual WAL target and RPO against acknowledged records. Never point restored storage at an unfenced production endpoint.
3. Start the restored writer with business traffic closed. Confirm native synchronous cross-AZ durability, primary clock bound and PKI. Apply additive schema migrations with controlled jobs; do not drop fencing/replay state or disable immutable triggers to make recovery easier.
4. Use `RecoveryEpochService.begin` with a verified permit binding cell, expected restored epoch, new epoch, **external pre-disaster high-water**, original recovery UUID and <=5s expiry. New epoch must exceed both the restored epoch and the external high-water. Run bounded `abortBatch` calls until no live restored call/home/reservation/session/boot/unquarantined-outbox/PENDING result remains. Wait for physical cleanup after every operation, including UNKNOWN.
5. Reapply the authoritative security/key-retirement cursor and privacy deletion journal through the restoration point to the current source high-water. Follow `privacy-after-restore.md`. Require signed replay-completion evidence bound to this recovery operation/new storage epoch, and verify the native security cursor/freshness.
6. Activate only after the native completion checks and refreshed directory/fencing/trust snapshots. Then controlled cell reformation, native readiness gates and bounded recovery scans. Observe first-cold-request and convergence separately. All restored nonterminal calls are aborted; do not resurrect media/control ownership to advertise continuity.
7. Record backup ID/restore target/WAL range, native epoch before/after/external high-water, fencing receipts, raw repair/replay results, target hardware/AZs, actual RPO/RTO and stale-work/old-node rejection. External evidence must use the exact candidate, never a TEST_ONLY fixture.

A directory PITR also requires outside-backup directory epoch high-water and coordinated source/target bucket fencing before publication. Do not treat old cached routing as authority. Until this separate regional recovery is qualified, release remains NOT_QUALIFIED.
